# MCP 授权的回调落在 API server 的回环路由上

授权流程的授权码由 API server 接收：浏览器被授权服务器重定向到
`http://127.0.0.1:<port>/api/mcp/oauth/callback`，这条路由挂在 `bearerAuth`
之前，因此不带令牌也能访问。

理由：交换授权码需要 PKCE verifier、动态注册得到的 client 信息与授权服务器的
pin，这三样都归 server 进程所有；回调落在别处就要把其中至少一样搬过进程边界。
桌面渲染端的文档源是 `aify-app://`，系统浏览器到不了；`aify-app://` 也没有注册
成操作系统协议，不能把浏览器拉回应用。所以能落在的地方只剩 server 自己。

代价：一条不带身份校验的路由。它只做三件事——按 `state` 找回待完成的流程、
用授权码换令牌、写一行记录。`state` 是 32 字节随机值，只存在于进程内存，十分钟
过期，用一次即删，并且不读取任何用户设置。

## Considered Options

- **渲染端接回调**：不加公开路由，但桌面里浏览器到不了 `aify-app://`，只能在
  `dev:web` 下工作。
- **手动粘贴授权码**：最省事，但用户要自己从浏览器地址栏抄一段字符串，且仍要
  注册一个可达的 `redirect_uri`。
- **回环路由（选中）**：桌面与浏览器开发模式都能用，交换留在持有 verifier 的进程里。

## Consequences

- `attach` 到远程 server 时，浏览器所在的机器不是 server 所在的机器，回环地址
  不可达。授权必须在宿主机上进行；桌面界面上会提示这一点。
- 回调路由的安全边界是 `state`，不是令牌。改动这条路由时不能顺手读取设置、
  不返回服务端错误详情、不把授权码写进日志。
- 发起授权时把服务器配置的快照放进待授权表；回调只认 `state`，从快照重建
  provider，因此不必读设置，换令牌用的也一定是发起时那份地址。
- 换到令牌后立刻重连一次，设置页当场看到「已连接」。
- 授权服务器地址必须过 `validateAuthorizationServerURL`：只放行 https 与回环，
  否则资源服务器可以把我们指向任意主机。
