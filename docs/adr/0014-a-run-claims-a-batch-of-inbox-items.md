# 一次运行领取一批待办项，而不是一条

一个会话的每次运行只领一条待办项（ADR 0012）。用户在运行中把投递方式切到 Queue 连发
三条，就得到三次运行、三条互相看不见的回复：第二条不知道第三条在排队。这个决定把领取
改成运行起点取收件箱里的全部待办项：每条仍是独立的 user 回合，按到达顺序排在一起，
回复只有一条，挂在最后一条之后。它取代 ADR 0012 后果里的「一次运行取一条待办项」，
其余部分不变。

理由：第一，Queue 的用户意图是「等你有空看这些」，不是「给我三份单独回复」。第二，
三次运行彼此看不见，第二条的回复可能和第一条打架，这在多任务场景里是实打实的错误。
第三，定时器落地后，「到点三条提醒」必然要求一次运行回答；领取策略先就位，定时器就不
必自己拼回复。

这不是为「运行中连发」做的。默认投递方式是 steering，运行中连发本来就会被插进当前
回合，那条路径已经合并过了。这个决定服务的是 Queue、重启恢复与暂停后继续时的积压，
以及定时器的前置。

## Considered Options

- **合并成一条 user 回合**（把 parts 拼起来）：丢身份。用户取消其中一条时无从下手，
  重发和 regenerate 也失去锚点。
- **第 2..N 条转成首个 assistant 步之前的 steering step**：steering 的语义是「插进正在
  跑的回合」，这些消息在运行开始前就到了。会伪造出「中途补话」的形状，也让 `turn.steer`
  承担两种含义。
- **只在发送端 debounce**：把合并策略放进浏览器，多端各写一遍，服务端仍然一次一条。
- **设批大小上限**：会造出「为什么第 17 条不在这轮」这条新规则，要解释、要测试、要界面
  表达。批里的内容只有用户消息，大小由人决定；真超窗口走溢出恢复，结果可见。
- **静默窗口**（例如 150ms）：给每条消息加固定延迟。而且「需不需要窗口」要对入队间隔的
  分布取证，今天没有证据。
- **失败时把整批退回收件箱**：同一批消息会有两份身份（turn 行与收件箱行），并把收件箱从
  事实来源变成重试队列，冲掉 ADR 0012 的取舍。
- **保留一次一条**：Queue 的三条会得到三次运行，正是要修的问题。

## Consequences

- 领取以事务里的删除结果为准：被取消的行退出批，其余照常跑，一条都不剩时按「已被领走」
  处理。调用方不预先算 `parentId`——部分取消会让预先算好的链指向没写进去的 turn，
  branch 从这里断掉。父链由 store 按领取结果重算。
- 收件箱行的 id 与 turn 的 id 不再要求相等。今天它们恰好相等；将来第二种 kind 接入时
  不必再改领取路径。
- `run.start` 带 `turnIds`。协议没有仓库外消费者（`agent-client` 是 workspace 内部包），
  所以直接改名，不留兼容字段。
- `findPreTurnPlacement` 改成向前找最后一条 assistant turn。批之后末尾是连续的 user
  回合，旧条件永远不成立，`before-turn` 压缩会被静默跳过一轮。
- 失败不退回队列：整批消息已经是记录里的 user 回合，暂停后「继续」重跑整批，重跑用的
  历史里已经有这些消息。
- 没有开关、上限、窗口。批大小大于 1 时打一行日志；这行日志只证明合并发生了，不能用来
  判断窗口——那需要入队间隔的分布。
- 词表不新增「批」：它是一次领取的结果，不是领域对象。`待办项` 词条里明确 Avoid
  「合并」。
- 子会话不走这条路径。它们没有收件箱，运行由父的工具调用同步等待。
