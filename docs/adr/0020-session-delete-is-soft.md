# 会话删除是软删除

「删除会话」保留会话行与转录，只把 `deleted_at` 写上；列表与读接口把已删会话当成不存在。
会取消的只有「将来还会发生的事」：定时器、未领取的待办项、发件项、会话的后台任务。记录
留在库里，等回收站那期。

## 形状

一列 `deleted_at`（可空时间戳），不加 `deleted` 布尔。时间戳同样是「一列 + 一个判别」，但
多带「什么时候删的」；将来回收站要做「删了七天再清」，不必再迁移一次。判别只有一个来源：
`deleted_at IS NULL`。

「已删 = 不存在」落在一个地方：`getSessionById` 不再返回已删行。回合、资源、工作区、事件流、
发消息全都经过它，过滤只需要写一次。写入路径显式报 `SESSION_NOT_FOUND`，不回退成重建——会话
行还在，`createSession` 的「已存在就返回」若照旧执行，一条旧消息会把删掉的会话唤醒成一次看不见
的运行。

运行中的会话不能删：一条流在跑就报 `SESSION_BUSY`，检查复用 `#assertIdle`。`wait_review` 可以
删：待审批住在转录里，不在内存里；恢复之后 `resume()` 照样能回答它，`#ready` 拒绝的只是新起
一次运行。

删除本身是一个事务：先按 `parent_session_id` 收子树，再 `UPDATE … WHERE deleted_at IS NULL
RETURNING` 认领（没命中就是已经被删过，返回 `removed: false`），然后按子树 id 删 `outbox_item`、
`inbox_item`、`timer`。`turn` 与 `step` 不删——它们就是回收站要恢复的转录。

没有外键兜底（SQLite 也没打开 `PRAGMA foreign_keys`），漏一张表只在库里留残行：不报错，也没人
看得见。所以带 `session_id` 的每一张表都要在一条测试里表态——跟着清，还是留着。

## Considered Options

- **删行**：表最干净，但回收站与「恢复」都没法做。用户已经说了以后要做回收站，这条出局。
- **`deleted` 布尔**：少一个类型。但时间戳在同一列里多带一条事实，回收站的清理窗口以后要用，
  而现在多一列的成本比将来再迁移一次低。
- **外键 + `ON DELETE CASCADE`**：只在删行时触发，而我们软删；而且级联只能表达「全删」或
  「全留」，表达不了「转录留、待办删」。它合适的时机是回收站真正清掉那次。
- **每条读路径各自过滤**：调用点分散在回合、资源、工作区、事件、发消息五处，将来加第六处就会漏；
  漏了不报错，只会让删掉的会话在某些路径上活着。统一在 `getSessionById` 过滤，漏不了。
- **发一个「会话已删除」事件，各自订阅清理**：清理必须是原子的，而事件在提交之后发；订户失败
  一半，就是「看不见的会话，定时器还在」。事件留在事务里同步跑，就退化成同一份清单换了写法，
  还多出隐式顺序。事件适合通知观察者（跨窗口刷新），不适合当清理协议。
- **删会话时把待审批一并拒绝**：要新增一条「补写工具结果」的写入路径，等于替用户做了决定；
  恢复以后转录里还会多出一条用户没做过的拒绝。不做。
- **归档与删除共用一列**：恢复时的语义说不清——回到原处，还是回到回收站？归档将来另起一列，
  本期不做。
- **连磁盘目录一起删**：记录都留着，目录却没了，恢复出来是一个有转录、没有产物的会话。目录跟着
  记录走，等回收站真正清掉时再删。
- **给模型一个删除会话的工具**：模型住在会话里，工具一开就能删自己或别的会话；删除是人的动作。

## Consequences

- 删掉的会话继续占库和磁盘，直到回收站那期。这是软删除换来的代价，要认。
- 任何绕过 `getSessionById`、直接查表的新代码会看见已删行。写在这里，是为了以后有人这么做时能归因。
- 回收站已经垫好：一个 `deleted_at IS NOT NULL` 的列表，加一个清空该列的动作。
- 待审批的会话删掉后，那个问题暂时没人看得见；恢复出来还在。
- 发件箱的候选查询 `innerJoin session` 只要求 `status='done'`，已删行仍是 `done`。所以未投递的
  行必须在删除事务里清掉，投递器不需要额外过滤。
