# 浏览器用进程级链接换登录态

浏览器不再依赖代理注入访问令牌：server 每次启动打印一条登录链接
（`/?token=…`，落在 web 源上），页面把票据 POST 给 `/api/auth/login`，换到
HttpOnly、SameSite=Lax 的 `aify_session` cookie，再把参数从地址栏抹掉。之后
的 HTTP 请求和 WebSocket 握手都靠它。票据不按时间过期，只绑定在签发它的那次
进程运行上：重启后旧链接失效，同一次运行里可以反复使用、也可以给多台设备用。
访问令牌只留给桌面主进程、CLI 和脚本。

理由：浏览器要能从局域网和远程打开，而代理注入要求两个进程共享同一份令牌
文件——这正是原来的痛点。URL 里放的不是长期访问令牌，而是一条只属于本次进程
运行的票据：重启就轮换，链接外泄也能靠重启收回。代价是重启前拿到链接的人都
能登录，也允许同一条链接在多台设备上使用——这是为“打开就能用”接受的取舍。
cookie 是唯一能同时覆盖 fetch、`<img src>` 和 WebSocket 的载体，因为浏览器
不让页面给后两者设请求头。

代价：浏览器第一次持有凭据，原先“页面永远看不到令牌”的规则只对桌面成立。
cookie 会被浏览器自动带上，所以鉴权中间件必须对 cookie 请求检查 `Origin`
和 `Sec-Fetch-Site`——`SameSite` 只挡跨站，不挡同站不同端口。终端也因此不再
限制回环地址，任何有效登录态都能起 shell。

## Considered Options

- **URL 里带长期令牌**：不用会话表，但局域网和公网下等于把 server 交出去。
- **Better Auth**：能做账号、密码和 OAuth；这个场景没有密码、没有多用户，它
  只剩登录态签发一件事，代价是四张表和一套要反过来锁掉的公开路由。
- **进程级票据换 cookie（选中）**：两张表加一个公开入口，和访问令牌并存；票据只随重启失效。

## Consequences

- 局域网明文 http 下票据和 cookie 都是明文；可信网络之外必须上 HTTPS。
- 同一条链接可以给多台设备用；链接丢了就重启 server 拿新的，或从已登录页面
  的设置里再生成一条。
- 链接落在 web 源上：有 `AIFY_WEB_ORIGIN` 就用它；没有时看开发服务器在不在；
  都不在就是 server 自己（同源托管产物）。`AIFY_PUBLIC_ORIGIN` 决定公网部署
  时的源和 cookie 的 `Secure`。
- 票据会出现在地址栏和历史记录里，而且在下次重启前一直有效：拿到这条链接
  的人就能登录。页面换完 cookie 会立刻把参数抹掉，但这只影响应用自己的 URL，
  终端里那条链接仍然可用。
- 票据行按 `instance` 归属进程，重启后旧行不再匹配；不做时间清理。
- 登录态 cookie 在每个带登录态的 HTTP 响应上重发一次：只滑动数据库行不会让
  浏览器手里那份跟着续期。
