# 供应商的密钥可以只记一个名字

中文副本。以 `0043-a-provider-key-can-be-named-instead-of-stored.md` 为准。

供应商自己持有密钥。设置把它和地址、模型清单存在同一份 JSON 里，于是这把密钥在 SQLite
文件里活到供应商被删为止，而且每一次读设置都会把它带回来。两种常见情况都不合适：

- 验收或 CI 要连真供应商。密钥本来就在环境里，再往一个用完就扔的库里写一份，等于多留
  一个没有人清理的副本。
- 有人把 API 跑在容器里，或者交给一个本来就会注入密钥的进程管理器。这时在表单里再填
  一次就是第二个真相，而且是更差的那一个。

供应商行现在可以只写一个环境变量的名字：

```json
{
  "id": "openai",
  "apiKey": "",
  "apiKeyEnv": "AIFY_PROVIDER_KEY_OPENAI",
  "models": []
}
```

两者互斥，引用在装配一次调用的时候才解析。

## 名字限定在一个命名空间里

`apiKeyEnv` 必须以 `AIFY_PROVIDER_KEY_` 开头。设置和供应商地址都是调用方写的；没有命名
空间，调用方就能把 `AWS_ACCESS_KEY_ID` 写成密钥，再把地址指向自己的服务，API 就会把那
个值发过去。前缀是命名空间，不是锁——操作者仍然能指名里面的任何变量——但它用一条规则
同时挡住了手滑和恶意。

命名空间还让每套部署用同一个写法：CI 里写 `AIFY_PROVIDER_KEY_OPENAI: ${{ secrets.OPENAI_KEY }}`，
应用一个字都不用改。

## 读不到的值在起跑处失败

密钥在装配模型请求的那个接缝上读，不是启动时读一次。两个后果都是想要的：

- 变量为空时，那一家供应商的一轮在起跑之前就失败，错误里点名这个变量。同一份设置里的
  其它供应商不受影响。
- 两次调用之间改变量，密钥就跟着变。没有任何一层缓存它。

存下来的 `apiKey` 为空仍然合法。旧行就是这样，而把一个合法的行变成不合法的行，等于让它
在下一次设置归一化时被丢掉。同样的理由：一条同时写着密钥和引用的存储行，在读取设置时
保留密钥、丢掉引用——密钥重建不出来，变量名能，否则这一行会连同它的模型一起消失。

## 这件事不做什么

环境变量不是保险库。同一个用户能把它读回来：`ps eww`，或者 Linux 上的
`/proc/<pid>/environ`。这个改动去掉的是持久化，不是暴露。真正靠得住的是短命、可撤销的
密钥——每次验收一把，验收完撤销。

## 被否掉的做法

- **密钥管理工具**（1Password CLI、SOPS、Doppler）。它解决的是密钥在静态时存在哪里，代价
  是每台跑验收的机器都要多一个依赖。环境变量是每个操作系统、每个 CI 都已经有的通道。
- **本地 broker**：密钥留在另一个进程里，应用只看见一个假密钥。这是最强的版本，这次推迟
  了：它必须不缓冲地转发流式响应，那是协议层的一块活，有自己的失败模式。它和现在的形状
  兼容——broker 只改变 `baseURL` 指向哪里。
- **隐式覆盖**：`AIFY_PROVIDER_<ID>_API_KEY` 压过存下来的值。最便宜，但它让一个字段有了
  两个来源：行上写着一样，调用用的是另一样。显式的字段才说得清哪一个在生效。

## 后果

- 设置界面保留这个字段、显示变量名，但既不能设置也不能删除它：手填一把密钥会取代引用，
  也没有办法走到「两者都没有」。在界面里选择引用是另一件活。
- 名字写错时走的是输入校验，所以点名命名空间的那句话落在校验问题列表里，不在界面显示的
  错误消息里。供应商弹窗显示的是消息，于是它现在显示「Input validation failed」。
- `setting/list-models` 接受同样的两种写法，因为密钥在环境里的供应商也要先拉一次列表
  才能存下来。
- 所有解析密钥的地方都走同一个函数。第二处直接读 `apiKey` 的代码会悄悄忽略这个引用。
