# 重试属于步的循环，不属于 SDK 参数

AI SDK 自带两层重试：`maxRetries` 默认 2，管请求发出之前的失败；`streamRetries`
默认 0，管流开始之后的失败。两层都关掉，重试放进回合循环：一步失败之后，内核在
同一个回合里开新的一步，用同一份历史重新请求同一个。代价是内核要自己写判定、
退避和预算；换掉的是一个在三处都不可见、不可数、也不分类的重试。

理由：第一，可见。SDK 的两层重试什么都不发。屏幕上只有空白，记录里没有一步，
日志里没有一行。收拢之后，每一次请求都是一步：有 `step.start`、有 `step_end`、
有一行记录。用户能看出这一段为什么慢，排查也能数清发了几次。第二，可数。SDK
的流中重试没有分类门槛：任何 provider 错误都重启，只有 `ToolChoiceViolationError`
例外。429 和 401 在它眼里一样，配额不足也一样。步的循环可以先判断值不值得重试。
第三，有界。两层叠起来，请求数是乘法：`maxRetries: 2`（3 次）加步级重试，数字
很快就说不清。关掉一层，上限只剩一个数。第四，部分输出有人负责。SDK 的流中重试
会把两次请求的文字都留在消费者流里（它自己的测试断言 `['partial ', 'recovered']`），
官方文档也说部分输出无法撤回、由应用决定去留。步级重试把「屏幕上留着、历史里
不留」写成一条规则，而不是留给 SDK 的行为习惯。

## Considered Options

- **留着两层（原状）**：零改动。但每一次重试都在暗处：不发事件、不写日志、不进
  记录，也不看是哪一种失败。
- **只打开 `streamRetries`**：比原状好一点，能补上流开始后的失败。但它同样没有
  分类、没有退避（错误后立即重试），还会丢掉失败那次的工具调用。一次 401 也能
  让它立刻重试一遍。
- **原地重跑同一个 `stepId`**：记录上最省。但协议是追加型的：part 按
  `[turnId, stepId, event.id]` 去重，而 `step.start` 复用 id 时只把状态拉回
  `streaming`，不清内容。屏幕会出现两段文字，记录里却是同一步。
- **手动重试按钮**：用户决定，不需要判定。但它要求回合已经结束、agent 已经
  `dispose`、`abortSignal` 已经作废，也就是必须是新的一次运行。它解决的是「重跑
  一轮」，不是「重新请求一次」。留给以后，建在同一套机制上。
- **步级重试（选中）**：内核在回合循环里判断、等待、重试。多发一次请求就多一步，
  记录、事件、钩子和 UI 都跟着这一步走。

## Consequences

- `maxRetries: 0` 之后，瞬时错误从 SDK 直接冒到步的循环。判定漏了某种错误，人会
  立刻看到失败，而不是被两次静默重试掩盖。这是有意的：掩盖比失败更难查。
- 文案 `Retry 1/5` 的数字只在重试上算，第一次请求不算。改
  `MAX_RETRIES_PER_TURN` 会同时改分母。
- 预算按回合，不按步。回合没有步数上限，预算是这一次运行唯一的界。
- 溢出重试共用同一个预算。压缩另有一道闸门：`MAX_COMPACTIONS_PER_TURN = 3`。
- `retry` part 必须留在投影之外，靠测试盯住。漏掉不会坏历史，但每次投影都会
  打印 `Unsupported part`。
- 失败的那一次不落行，也不进历史：投影跳过以失败收尾的步。它的半段文字留在
  当时的屏幕上，刷新之后消失。这是「没有结果就没有行」的直接后果，不是新加
  的取舍；唯一的代价是这段文字不在任何地方留下痕迹。
- 关掉 SDK 重试之后，请求挂住仍然没有界。超时会把「模型慢」变成「模型失败」，
  需要自己的阈值和文案，另开一条。
