# 图片在读取时规范化一次

中文副本。以 `0037-an-image-is-normalized-once-at-the-read.md` 为准。

读取过去原样透传源字节。这对一张小截图成立，对人真正拥有的东西都不成立：手机照片是几
兆像素，路由反正会缩；横拍的照片把旋转放在 EXIF 里，模型看不见；16-bit PNG 或 CMYK JPEG
是某些 provider 直接拒绝的格式；Mac 上的 HEIC 是这里没有任何东西能读的格式。上一期的上限
把每一种都变成拒绝——诚实，但没用：用户有一张图，助手说不行。

现在读取会解码，存一份规范化副本：单帧、8-bit、sRGB、无元数据、长边至多 1568 px、总计至多
1.15 MP，编码为 1 MB 以内的 WebP。存下来的字节就是这份副本，源文件留在原处。方向应用后的
源尺寸记在引用上，信封告诉读者怎么把在副本上量到的坐标换回原图。

解码器是 sharp，按需加载。原生二进制缺失的部署保留只看文件头的路径：它仍然知道尺寸、仍然
拒绝处理不了的东西、仍然能回答。打包产物会带上平台包，缺失时打包失败，而不是悄悄少一项能力。

## 被否决的选项

- **原样透传，让 provider 自己缩**：零依赖、零 CPU。它留住了方向、深度和格式三类失败，还要付
  上传与重放的代价去送没人会按原尺寸看的字节。
- **只在源超出上限时规范化**：大多数准备好的截图会跳过这一遍。它把存储形态分成两种——有时
  WebP，有时 PNG——于是路由、存储、字节估算各多一个分支。
- **一律规范化**（本决定）：一种存储形态、一种媒体类型、一个字节预算，坐标提示只有一个含义。
  代价是每次读图都要解码再编码，并且丢弃原始字节。
- **用 JavaScript 的图像库解码**：没有原生二进制，可移植。但支持 HEIC 与 16-bit TIFF 的纯 JS
  解码器比 agent 其余部分加起来还慢还大，而且 12 MP 的 JavaScript 解码会阻塞事件循环。

## 后果

- 每张图都要解码加编码。护栏把代价框住：压缩至多 64 MB、解码至多 100 MP，解压炸弹在像素产生
  之前就被拒绝。
- 存下的副本比源小，所以会话重放送出的正是模型看过的东西，而不是它的又一次缩放。
- sharp 是带平台包的原生依赖。它和 ripgrep、libsql、node-pty 一起进打包脚本；缺失时跑的正是
  那条回退路径。
- 原始文件不保留。需要全分辨率的读者必须重新读文件，所以信封保留了源路径与倍数。
