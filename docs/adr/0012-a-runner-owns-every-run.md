# 运行由一个运行器启动，不留给调用方

一个会话同时只有一条运行。今天这条不变式由三处各管一段：网页在收到
`SESSION_BUSY` 时把消息塞回队列，压缩自己查一遍注册表，子会话自己建流。重设计把它
收进一个对象：运行器持有唯一的锁，也是唯一启动运行的代码。HTTP 层只能往收件箱写一
行，然后唤醒它。代价是删掉客户端起跑那条路，运行器成为单点。

理由：第一，不变式从错误码变成结构。今天「已经有一条运行」是一个拒绝，拒绝方必须
处理它：网页会排队，别的调用方不会。不再有第二个起跑者之后，所有调用方都不用写那段
处理。第二，唤醒可以丢。每次运行结束都会再看一眼收件箱，所以「谁在什么时候唤醒」是
延迟问题，不是正确性问题。这是能承受单点的原因：唤醒少了一次，最坏是晚一轮。第三，
常驻的前提是有人替用户推进。定时器、外部事件以后只要往收件箱写一行，不需要各自知道
怎么起跑。反过来说，「服务端决定何时跑」成为唯一事实之后，客户端也不必再猜会话忙不
忙。

## Considered Options

- **保留客户端起跑，运行器只做兜底**（宽限期）：增量最小，网页可以不动。但两条路要
  长期对「怎么把待办项变成回合」和「跑完了意味着什么」保持一致，而且总有一条路没被
  日常流量覆盖。
- **运行器独占，另留一个开关退回客户端起跑**：开关本来是想兜住单点。但独占之后客户端
  那条路已经删了，开关只能「全停」，退不回去。要真能退，就得把两条路都留着，回到上
  一条。所以开关不是退路，是额外的维护成本。
- **把压缩也放进收件箱**：压缩不是模型回复，它在等待审批时必须被拒绝，规则和消息不同。
  它被当成一次运行登记，所以共享同一把锁，但不进队列。
- **运行器独占，不留退路**（选中）：单点的风险用可观测性和测试兜。

## Consequences

- `SESSION_BUSY` 在消息路径上消失，只剩压缩用它。
- 运行器挂了，所有主会话都发不出消息。队列深度、正在跑的会话、暂停原因必须看得见，
  否则单点等于黑箱。
- 子会话的运行不走运行器：它必须和父的工具调用同步等结果。所以准确的说法是「主会话
  的模型回合只由运行器启动」，不是「所有运行」。
- 一次运行取一条待办项。合并多条要等到定时器落地，那时「三条提醒合并成一次运行」才
  合理，因为它不期待三次回复。
- 暂停是运行器的内存状态，不落库。重启后队列继续跑，用户按下的「停」不跨重启。
- 客户端订阅的是会话，不是运行。运行结束后连接保持，下一次运行开始时接着推。
- 队列由服务端推进，网页不再自己发下一条。网页把消息写进收件箱就结束，结果从会话
  事件流上看；「谁排队、谁先跑」因此只有一个答案。
