# 子代理可以再被递话

中文副本。以 `0042-a-subagent-can-be-messaged-again.md` 为准。

子代理曾是一片同步的叶子。委派的助理发一次工具调用，调用不返回直到子代理结束，而子代理的
Agent 在它的流结束时就被销毁。再给它递第二句话是不可能的：子会话拒绝一切不来自「派生它的
那次调用」的运行。

同一个形状造成三个互不相同的问题。助理在子代理干活时什么都做不了，所以一条消息里发多个委派
仍然要付它们运行时间之和。干到一半的结果没法追问，除非从一份 brief 重新开始，而新的子代理
什么都没读过。跑偏的子代理停不下来，因为助理正卡在「本来可以让它停」的那次调用里。

现在委派启动一次运行就返回。调用回一个名字，子代理落定时变成一条完成通知，另外三个工具能在
它运行中或汇报之后够到它。

## 调用不再等待

子代理的寿命现在是父会话的寿命，不是父那一轮的寿命。它在父会话被停或被归档时停止，并且能活
过启动它的那一轮结束。第一版把它绑在父那一轮上，因为那一轮是唯一持有子 agent 的 abort 作用域
的东西；保留这个绑法等于在那一轮结束时杀掉每个子代理，而这正是后台委派不能做的事。

## 容量满了就拒绝，不排队

一个会话可以同时跑固定数量的子代理。超出这个数的委派会被拒绝，并附一句模型能照着做的话：等
一个跑完，或者停一个。

排队被否决了。只要每个槽位都属于「自己也在等子代理」的助理，等容量就会死锁，而这个运行时里
没有任何东西能把那个状态和普通的慢区分开。拒绝一步就能恢复；死锁不能。

只有正在跑的子代理占位。已经汇报、正在等消息的子代理不持有模型流，也就不占槽位。

## 重跑同一个调用是追加，不是丢弃

那次调用本来就靠工具调用 id 幂等：同一个调用重跑，会找到它的子会话，接着那段会话记录往下走。
它同时把新的 brief 丢掉，因为重试的调用被假定带着同一份 brief。

现在既然可以有意地递话，一条路就够了。重跑的调用把它的 brief 追加给同一个子代理，和递话完全
一样。通向同一段会话记录的两条路会漂移，而丢弃的那条会把一个静默的缺陷一直留着。

## 后台工作不落定就是静默的

同步调用卡住是看得见的：助理卡在它里面。后台子代理卡住是看不见的——没有任何东西被阻塞，会话
只是安静下去。

所以每次子运行都有一个墙钟时限，默认给得足，到时把运行落定并发通知。服务启动时也会落定上一个
进程留下的运行并发出它们的通知：收尾那条路本来就在做这件事，只是没有通知在等它的人。

## 通知报告事实，不写指令

完成通知带着名字、类型、终态和报告。它不点名任何工具。后台任务的通知会点名，因为它的载荷是
一个指向太大输出的指针；子代理的通知自带答案，没有东西要去取。

那句属于每一次委派的话——不要轮询，结束回合——住在子代理目录里，和其余指引在一起。写进每条
通知的规则会是「已经有家」的规则的第二份副本。
