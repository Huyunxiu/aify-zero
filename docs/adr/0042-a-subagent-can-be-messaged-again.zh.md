# 子代理可以再被递话

中文副本。以 `0042-a-subagent-can-be-messaged-again.md` 为准。

子代理曾是一片同步的叶子。委派的助理发一次工具调用，调用不返回直到子代理结束，而子代理的
Agent 在它的流结束时就被销毁。再给它递第二句话是不可能的：子会话拒绝一切不来自「派生它的
那次调用」的运行。

同一个形状造成三个互不相同的问题。助理在子代理干活时什么都做不了，所以一条消息里发多个委派
仍然要付它们运行时间之和。干到一半的结果没法追问，除非从一份 brief 重新开始，而新的子代理
什么都没读过。跑偏的子代理停不下来，因为助理正卡在「本来可以让它停」的那次调用里。

现在委派启动一次运行就返回。调用回一个名字，子代理落定时变成一条完成通知，另外三个工具能在
它运行中或汇报之后够到它。

## 调用不再等待

子代理的寿命现在是父会话的寿命，不是父那一轮的寿命。它在父会话被停时停止，并且能活过启动它
的那一轮结束。第一版把它绑在父那一轮上，因为那一轮是唯一持有子 agent 的 abort 作用域的东西；
保留这个绑法等于在那一轮结束时杀掉每个子代理，而这正是后台委派不能做的事。

## 停止要多回答一个问题

停止按钮只问了一件事，却表达了两件：结束这一轮，以及结束它拉起的一切。现在这两件事是控件上
的一个选择，因为另一条路让规则去猜。

为了让这个选择存在，继承下来的 abort 作用域必须去掉。子 agent 曾继承父的 abort 信号，而信号在
构造时就把答案钉死了——把子代理一起带走。现在由会话层在停止的那一刻决定：默认把它们一起带走，
因为一个让子代理继续写文件、继续烧 token 的停止不叫停止；另一个答案只停这一轮。

被留住的子代理照常汇报，而它的汇报不会开一轮。父会话因为被取消而暂停着，所以通知躺在收件箱里
等下一次有人说话。这才让「留它在后台，我晚点回来」成为真话，而不是屏幕上兑现不了的承诺。

被一起带走的子代理不写通知。用户要的就是这次停止，父会话的下一轮不该以「停止发生了」开头。
自己跑完的那次运行照旧汇报：停止没有从它那里拿走任何东西。

删除不问。一个要消失的会话不能持有正在跑的子代理，而报告要落进去的那几行正是这次删除要移走的
行，所以删除会先带走子代理，再移走任何东西。

## 容量满了就拒绝，不排队

一个会话可以同时跑固定数量的子代理。超出这个数的委派会被拒绝，并附一句模型能照着做的话：等
一个跑完，或者停一个。

排队被否决了。只要每个槽位都属于「自己也在等子代理」的助理，等容量就会死锁，而这个运行时里
没有任何东西能把那个状态和普通的慢区分开。拒绝一步就能恢复；死锁不能。

只有正在跑的子代理占位。已经汇报、正在等消息的子代理不持有模型流，也就不占槽位。上限是 8，
由 `AIFY_SUBAGENT_LIMIT` 在启动时给出。

数名额和它把守的那次起跑是同一步。数清楚几个在跑、把新的一条登记进注册表，中间隔着几次
await，所以同时到达的两次委派会数到同一个数字、各自起一条——上限就只是提示，不是上限。
这个会话关于子代理的每个决定都过同一把锁：起跑、落定后开下一轮、叫停。锁按父会话记，不按
持有工具的那个对象记，因为那个对象是每次父运行新建的，而子代理活得比它久：落定发生在后面
某一轮的那一份里。

落定后开下一轮不需要自己再查一次名额。它在同一个加锁的步骤里交出槽位、又拿回下一个，
它看到的数字就是它留下的数字。

在库里查名额被否决了。名额的真相在进程的流注册表里，不在某一列上，行约束数的是另一个
东西——而能看到真相的那个进程，正是必须把起跑排成一队的那个。

## 重跑同一个调用是追加，不是丢弃

那次调用本来就靠工具调用 id 幂等：同一个调用重跑，会找到它的子会话，接着那段会话记录往下走。
它同时把新的 brief 丢掉，因为重试的调用被假定带着同一份 brief。

现在既然可以有意地递话，一条路就够了。重跑的调用把它的 brief 追加给同一个子代理，和递话完全
一样。通向同一段会话记录的两条路会漂移，而丢弃的那条会把一个静默的缺陷一直留着。

至于这句 brief 落到哪里，由子代理的状态决定，不由调用决定。对着一个正在跑的子代理，它变成一条
待领项，子代理在下一步读到；它不起运行，也不占槽位，因为它没有多出一次运行。对着一个已经停下
的子代理，它确实会起一次运行，于是要占槽位，也可能像别的起跑一样因名额被拒。

## 后台工作不落定就是静默的

同步调用卡住是看得见的：助理卡在它里面。后台子代理卡住是看不见的——没有任何东西被阻塞，会话
只是安静下去。

所以每次子运行都有一个墙钟时限，默认一小时，到时把运行落定并发通知。`AIFY_SUBAGENT_TIMEOUT_MS`
在启动时给出这个数，和名额那个旋钮放在一起，因为两者都还没有设置界面。服务启动时也会落定上一个
进程留下的运行并发出它们的通知：收尾那条路本来就在做这件事，只是没有通知在等它的人。

## 通知报告事实，不写指令

完成通知带着名字、类型、终态和报告。它不点名任何工具。后台任务的通知会点名，因为它的载荷是
一个指向太大输出的指针；子代理的通知自带答案，没有东西要去取。

通知不是「换了个发信人的任务通知」。生产者把两个值一起交出去：它在收件箱里记
什么种类，它变成回合后 step 上记什么来源。所以一条落定不可能以「后台任务」的
身份到达——父会话在会话记录和收件箱里读到的都是子代理。

writer 是一项能力，不是一个端口。它最初是服务端建出来、在运行器构造完成之后才绑上去
的对象，于是「落定某件事」的那一层要靠上一层告诉它运行器在哪。现在运行器自己建出唯一
的那一个，并把它交给每一次装配：扩展够到自己的会话，和它够到存储是同一条路。子代理
故意不给这一个——它靠自己的会话记录汇报。

那句属于每一次委派的话——不要轮询，结束回合——住在子代理目录里，和其余指引在一起。写进每条
通知的规则会是「已经有家」的规则的第二份副本。

## 递过去的一句话，以一条待办项的形式等在收件箱里

父代理递给子代理的那句话，作为一条待办项等在子代理自己的收件箱里，因为这一行
活得比写它的那次调用久：子代理可能跑完、被叫停、或者进程没了，行仍会把这句话
带到下一个读它的运行面前。

这句话最后变成什么，由交付边界决定。正在跑的那一轮会在下一个步边界领走它，它
作为插话落进那一轮；其余情况等下一次运行，由那次运行在写回合的同一个事务里领取。
这条规则属于收件箱（`resolveDeliverAt`），不在这里留副本。

同一个子代理同时只有一次运行在领取。父代理可能正好在前一次运行结束的那一刻递话，
而那次运行的收尾也会去找还有什么在等，所以两条路都要经过下面说的那把锁。

自己正常结束的运行会为读不下的待办项再开一轮，所以父代理不必把同一句话说两次。
被取消或失败的运行不会：没有人会再起这个子代理，它的落定通知会把没读的待办项丢掉
并说清丢了几条。`wait_review` 是例外，那次运行是停在那里，不是结束。

叫停子代理同样会丢掉它在等的待办项，`stop-agent` 会报出条数，因为本该读它们的那一轮
正是被停掉的那一轮。父会话被停则不动它们：那个会话再跑起来、又给这个子代理递话时，
旧的那几句会按顺序排在新句子前面。

重启本身不递送任何东西。待办项等到父会话再次运行这个子代理时才被读，并且排在新句子
前面。启动不唤醒子会话，所以这中间没有东西会跑它。

一次结算一条通知，不是每个子代理一条：同一个子代理可以结算多次，第二条通知不能被当成
第一条未读通知的重复而丢掉。

这一行给不了的，是重试下的精确一次。一条待办项被领取之后，同一次调用再跑一遍会写下
第二条，于是同一句话可能被读到两次；反过来丢不了：领取和写回合在同一个事务里。

行需要一个模型：行的形状要求它，子会话的会话行不带它。`send-message` 记下这个子代理
会用的那个模型。运行也按同一条规则解模型，所以记下的副本只有在父会话中途换了模型时
才不一致——那时以运行为准。

子会话仍然被运行器的收件箱入口拒绝，启动也不再唤醒它。它的下一次运行由握着它名字的
那次调用开启，一次唤醒只会报告一场不会发生的运行。

## 会话记住它上次起跑用的载荷

崩溃留给父会话的那条通知，是下一个进程写的，而那个进程从没跑过这个会话。唤醒一次运行
需要一份载荷，而那份配置只存在内存里，所以通知写进了空气：唤醒碰到空收件箱，运行没有
开始，写入方等超时后放弃。

于是运行把它的载荷写回会话行，恢复路径把这份快照交给写入方——和定时器为同一个理由携带
的那份同形。没有快照的会话被跳过并记一条警告：从这一列存在起它还没跑过，没有可唤醒它的
东西，也没有可告知的内容。

通知还会带上子代理已经说过的话，以及它结算成什么。崩溃并不让每次运行都算失败：已经答完、
只是没清掉标记的那次，结算成 done。空的回答仍算失败，和活着的结算用的是同一条规则。

有一种情况仍然看不见：存下的模型已经不可配置。写入会成功，唤醒的那次运行起不来，运行器
记一条日志并暂停；通知留在收件箱里，下次启动按过期清掉。要在这里发现它，就得在启动路径上
读模型配置，而这个进程不读。

撤回在这里没有对应物。后台任务的通知会在模型先读走输出时撤回自己；子代理的通知
自带答案，没有东西会在带外消费它，也就没有可撤回的东西。
