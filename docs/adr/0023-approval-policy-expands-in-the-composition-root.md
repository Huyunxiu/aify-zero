# 审批策略在组合根展开成决策，执行器不认识档位

会话加了一个审批档位（标准、编辑、只读、全放行），用户选择存在
`session.approval_policy` 里。它在 `createSessionAgent` 里展开成
`ToolApprovalPattern`，与宿主规则（MCP 注解）折叠之后交给执行器；执行器和判定
层照旧只认 allow / ask / deny 三个答案，按档位分支的代码只有 `effectivePolicy`
一处 —— 它回答的是「这次运行按哪一档跑」，不是「这次调用能不能跑」。

档位回答按**审批类别**给出（读取、改动、命令、交互、未知），不按工具名。类别表
是内置工具的唯一清单，MCP 工具用服务器自己的注解；查不到注解就是未知，比按读取
放行安全。这张表同时取代了原来硬编码的 `DEFAULT_TOOL_APPROVAL_TOOLS`，所以「谁
该问」只剩一处权威。

四条不能改的规则：

- **拒绝最优先。** 档位只能放松「问」，翻不过 hook 和宿主规则的拒绝；只有只读
  档对改动类给 `deny`，它是封顶。未知类别（例如服务器开了 `autoApprove` 的 MCP
  工具）在只读档下不表态：我们不知道它会写什么，就不假装知道。
- **已知危险不放松。** 全放行放松的是「不知道它做什么」的那类询问 —— MCP 服务器
  没给注解、默认要问。服务器明确给了 `destructiveHint` 时，它的 `ask` 不能被放松：
  用户说的是「不用问我你拿不准的事」，不是「不用问我它自己都承认会破坏的事」。
- **hook 的 `ask` 不放松。** 那是代码而不是默认值提出的问题，人的快捷方式不该越过
  代码写的保护；能越过它的只有用户当场作答。
- **无人值守收紧。** 由定时器或完成通知唤起的运行按标准档装配，编辑与全放行都
  退回去：没人看着的时候，自动放行改动正是最不该生效的时刻。收紧发生在运行器
  里，那里才知道一次运行是被谁唤起的；库里始终存用户选的档位。
- **子会话继承生效档位。** 子代理的行和 fork 出来的行都抄父/源的值。不抄的话
  它们会静默回到标准档，父里放行的事换个会话又开始问。

## Considered Options

- **执行器里加一个 bypass 分支**：改动最小，但「能不能跑」就有了第二个判断处，
  和「一个判断只有一个权威」相悖；hook 与宿主规则也要各自再让一次路。
- **环境变量选档位**（`AIFY_SANDBOX_ADAPTER` 那种做法）：用户会中途改档位，环境
  变量改不了运行中的进程，也留不下会话级的记录。
- **每个工具一个布尔开关**（`autoApprove`）：组合数随工具增长，且回答不了「命令
  算不算改动」。
- **存进 `session.metadata`**：省一条迁移，但那列装的是不参与判定的东西；档位要
  参与判定，放进去等于每次使用都先把它打开。
- **档位做成第五个值 `auto`（让模型判断风险）**：判定是概率组件，它只应该放松
  「问」，不该成为档位表里的一行 —— 否则一张纯函数表要等一次网络调用。判定端口
  留给以后，界面上以「标准 + 判定开」的组合出现。

## Consequences

- `edit-file` 从「不问」变成「标准档要问」。这是补漏，不是新策略；`bash` 仍然
  不问，改它需要单独一篇 ADR（那是一次影响所有人的手感变更）。
- 只读档拒绝 `bash`：它是唯一新增的硬保护。读工具在任何档位都不多问一次。
- 「生效档位」不入库，所以历史运行查不到当时用的是哪一档；要按运行追溯时，在
  `run.start` 上补一个字段是加字段的增量改动。
