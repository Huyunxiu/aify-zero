# 假供应商把场景和协议分开

假供应商是一个按供应商协议应答的本地服务，用来在没有真实供应商时跑完一次对话或
一次失败。它的场景是协议无关的 JSON：只说「第几次请求做什么」，不说 SSE 长什么样。
协议知识只活在每种协议各一个的**写手**里。场景里不提供 `raw`（直写字节）或自定义
写手这类逃生口；要新的失败形状，就往结果表里加一个结果。

理由：第一，一份场景两种消费者。手动点着看和自动化测试读的是同一个文件，所以人验
过的场景，测试里跑的就是它，不会出现「脚本里是 429、测试里是 503」这种漂移。第二，
加协议不等于重写场景。仓库有两种协议（`openai-chat`、`openai-responses`），把 SSE
的形状写进场景，等于把第一种协议钉死在每一个场景里；分层之后加第二种协议只是加一个
文件。第三，可读性就是它存在的理由。`raw` 逃生口看起来省事，实际会把场景变成没人
愿意读的协议草图；而「加一个结果」是十分钟的事，代价远小于维护一条什么都能写的旁路。
第四，它补的是一段真空。今天自动测试把 `streamText` 换掉，`gateway.ts` 到
`createOpenAICompatible(...).chatModel` 这一段一个测试都没有；手动验证靠一次性脚本，
用完就丢。这两件事都该由同一个东西承担。

## Considered Options

- **继续用手写脚本（原状）**：零成本。但脚本活不过一次会话，每个想验失败的人都要
  重写一遍；而且它只是给人看的，测试用不了。
- **用 `msw` 拦 `fetch`**：进程内、不用端口。但服务端是独立进程，手动测试仍需要真
  端口；而且它拦的是库的调用，不是协议本身，SSE 的分帧与头部仍要自己写。
- **把场景写成代码**：类型安全，测试直接 import。但改一个数字要改代码，手动跑还要
  经过 `tsx`，场景也不再是数据。
- **通用 `chunks` / `raw` 脚本**：什么都能表达。但场景会退化成协议草稿，可读性没了，
  而可读性是它存在的第一个理由。
- **场景与协议分离（选中）**：一个结果表，每种协议一个写手。加失败加一行，加协议加
  一个文件。

## Consequences

- 加一种失败要改代码，不是改 JSON。这是有意的门槛：结果表是这份工具的词汇，词汇
  应该被审过，而不是每次现场发明。
- 某个协议表达不了某个结果时，写手要报「不支持」，而不是悄悄降级。静默降级会让
  「测过了」变成假话。
- 录制进版本库需要人挑。fixtures 里带着提示词与答案，默认落在 gitignore 的目录；
  入仓的那些要脱敏过。
- 回放会重跑副作用：工具在宿主机上会再执行一遍。要没有副作用，工具也得换成假的。
- 它不进设置预设，也不进 `GLOSSARY.md`：它是开发工具，不是产品的一部分。哪天它
  变成产品能力（比如一个演示模式），这两个决定都要重看。
