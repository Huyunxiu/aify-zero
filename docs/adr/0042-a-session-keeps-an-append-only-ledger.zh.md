# 会话保存一份只追加的流水

> 中文副本。以 [`0042-a-session-keeps-an-append-only-ledger.md`](./0042-a-session-keeps-an-append-only-ledger.md) 为准。

昨晚发生的故障，今早读不出来。三个事实决定模型为什么那样做，而它们都没活过那次运行：

- 模型路线是每个回合决定的。`turn_start` 钩子能改它，而回合行上没有任何字段装它。
- 审批策略是每条运行读一次。只存会话的当前值，所以改一次，之前每个回合都读不出来。
- 装配出来的系统提示词一个字都没存。`turn` 和 `step` 两张表没有 instructions 列，而 `bot.instructions` 是静态文本，不是装配结果。

会话记录还有一处会藏起来的损耗。写路径是最新状态的 upsert：先插一条 `streaming` 的回合，`step.finish` 只在步骤没失败时 upsert 一行，所有 delta 丢掉。崩溃时在飞的步骤什么都不剩，恢复用一个扁平的理由把回合标成 `error`。重新生成会覆盖那一行，早先的答案不留痕迹。

事件通道也帮不上。它只在内存里装一次运行，每次 `turn.start` 清空缓冲，跑完的运行改从数据库重放。那条流是屏幕，不是记录。

所以一个会话在会话目录旁边保存一份只追加的记录文件。会话记录仍是视图，流水成为证据。回放读流水，绝不重跑模型，因为模型不确定，工具的作用不能重复。

## 考虑过的方案

- **SQLite 里加一张 `event` 表，会话记录做它的投影**：教科书的形状，而且可查询。代价是每个事件都在热路径上多一次写，要一条迁移，还引出这个功能今天答不了的那个问题：投影和日志不一致时听谁的。
- **把 `step` 改成只追加，加一列 `superseded_by`**：改动最小。粒度就停在步骤上，于是 delta、审批、收件箱的因、生效值都装不进来，而最要紧的正是这几样。
- **复活未合并的 `aify0-89` tape**：一个带版本号的 JSONL 记录器，录在 provider HTTP 层，已经写好了。它录的是模型收到了什么，不是人做了什么：领取、插话的一句话、一次审批、一次压缩，在那层一个都看不见。它留在测试用途。
- **引用会话记录，不复制内容**：文件最小。重新生成会覆盖那一行，早先的尝试只剩一个 id。这恰好坏了这个功能唯一的要求。
- **会话目录旁边一份 JSONL 文件**（本决定）：不加迁移，不改会话记录的热路径，一次追加失败也传不到运行上。代价是步骤内容有两份，以及一个要读很多年的格式。

## 后果

- 步骤内容存在两处，流水那份大致是第二份字节。这份重复是「保住被覆盖的尝试」的价钱。
- 流水装的是发生过什么，不是它是什么意思。含义变过的记录按原样显示，不重新解释，所以旧会话的回放可以既忠实又没用。
- 失败步骤的 delta 在内存里等到失败为止。被 kill 的进程保住失败点，丢掉里面的打字过程。
- 流水永远不修会话记录，会话记录也永远不修流水。需要两边事实的读者要说清自己读的是哪一份。
- 新增生效值要升行版本。旧行保留自己的版本，显示「这份记录没有这一项」，因为填默认值等于描述一个没发生过的过去。
- 读路径是一条压在文件上的路由，所以回放视图可以建好再扔掉，不用改表结构。这就是这个决定可撤销的原因：删掉文件，历史没了，而产品从来没有依赖它。
