# 录制带记录外部输入，不记录系统状态

调试「运行中才出现」的界面需要一个可重复的运行窗口：插话与排队、审批、重试、压缩、
任务通知，都只在运行期间成立。今天的做法是让假供应商慢一点，靠猜秒数。本决策引入
录制带：一次会话的外部输入按时间录下来，之后可以原速播放、逐帧步进、中途挂起。

录制带记的是外部世界，不是系统状态。模型响应按原始字节存，带相对时间戳；用户输入
按时刻存，回放时重新写进收件箱。工具结果不单独录：它作为下一次请求的 `messages`
自然出现在请求体里。

理由：第一，事件溯源解决的是「状态怎么重建」，这里要解决的是「不确定性怎么消除」。
系统状态已经由会话记录持久化，重放它没有意义；有意义的是固定四类外部输入——模型
输出、工具副作用、时间、调度顺序。第二，四个接缝已经在仓库里（供应商、沙箱适配器、
运行器单锁），插驱动比新建架构便宜。第三，按字节存而不是按协议事件存，回放时不必
重新编码，链路最短；事件边界作为索引另存，不构成第二份真相。

## Considered Options

- **事件溯源**：把所有输入与派生事件折成一条日志，重放折叠过程。它能重建状态，但
  副作用不在事件里：工具真的写过磁盘，重放第二次会腐坏。要让它成立，还得叠一层沙箱
  快照，成本高出一个量级，而目标是调试界面，不是审计。
- **录 AI SDK 归一化后的 chunk**：语义更贴近界面，但回放时要重新编码成 SSE 才能送进
  假供应商，多一层转换，且转换本身需要测试。
- **扩展假供应商的场景语言**：给 `slow` 一个更长的版本。最小，但时序仍然靠猜，且
  只能停在流开始之前，停不到工具调用与下一步之间。`slow-answer` 的三秒等待就是这个
  方案的现状。
- **录制带 + 可控时钟**（选中）：假供应商退回成响应回放器，时间轴由 server 侧的重放器
  执行。时间轴要写收件箱，而供应商不知道会话是谁，所以执行者只能是 server。

## Consequences

- 录制带是 PII：请求体带着提示词。入仓的样本要过脱敏，本地录制继续忽略。
- 帧级不可倒退：SSE 是单向流，已经发出去的帧收不回来。面板不提供「上一帧」。
- 挂起有硬上限：undici 默认 `bodyTimeout = 300s`，靠 SSE 注释行保活。
- 前端的渲染节流（200ms）让「一帧一渲染」不成立。播放按数据步进，调界面时另开关节流。
- 旧 `replay` 动作与新播放并存一段时间，读同一份录制的两条路要标清哪条是旧的。
- 输入事件由 server 通过控制面推给供应商，录制带始终只有一个写入方；代价是 server 侧
  多一个 dev-only 的钩子，它漏掉的事件不会出现在时间轴上。
- 面板暂时由供应商提供（`GET /__tape/panel`）：重放器还没落地，播放控制先能用。
  等时间轴需要投递输入事件时，面板要跟着重放器搬到 server。
