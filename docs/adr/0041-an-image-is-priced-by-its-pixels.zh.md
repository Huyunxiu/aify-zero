# 图片按像素计价

中文副本。以 `0041-an-image-is-priced-by-its-pixels.md` 为准。

上下文计量对每张图一律记 1500 token。那个数是占位符：估算函数量的是模型消息，而模型消息里的
file part 只写媒体类型。尺寸在附件引用里，估算函数看不到。

误差两头都有，偏低那头更常见。满尺寸的副本按 P/750 是 1536 token，所以 1500 在大图上从来不是
问题。一块 400×300 的裁剪真实成本约 160 token，却记成 1500：九倍，而且这段历史活着的每一轮
都按它计价。`region` 让这种情形变成常态。一个裁二十次的会话，估算凭空多出 2.7 万 token，压缩
提前触发，还能用的历史被摘要掉。

现在价格从图本身读。file part 仍然带着字节，头部就能回答尺寸问题，一条公式服务所有供应商：

```
tokens = clamp(ceil(width * height / 750), 85, 1536)
```

P/750 是 Anthropic 的精确口径，在读取存下的尺寸上，与 OpenAI 瓦片法相差不到一成。85 是一个
瓦片，明细规则对图片的最低收费。1536 是规范化像素预算按 P/750 折出的数：供应商在收费前会先把
图缩到自己的明细预算，所以读取存下的东西不会比这更贵。

PNG、GIF、WebP 在前 32 字节里就声明尺寸。JPEG 把帧头藏在相机写入的元数据段之后，所以读取会
先扩到 4 KB、再扩到 64 KB，然后才判定它没有声明尺寸。凡是量不出来的——这种情况、URL、provider
引用——一律按天花板算。偏高会让压缩提前，偏低会让请求在花完钱之后溢出。

## 考虑过的方案

- **按 `toolCallId` 反查**，由仍然持有引用的 step 提供：精确，而且键已经在消息里。代价是把
  resolver 穿过四个调用点，而且它算不了用户自己上传的图——那种图不属于任何工具调用。
- **在投影时把价格写进消息**：消费端最省。它把机器读的数字塞进模型读的内容里，而模型会读到。
- **两本账**：消息按占位符估，再从 step 补差价。一个数字两个真理，压缩阈值会在两者之间漂。
- **读 part 里字节的头部**（本决定）：不用管线，一个真理，也覆盖上传的图。代价是每个被计价的
  part 多做一次 base64 切片，JPEG 再多两次。

## 后果

- 估算仍然是压力表，不是账单。有 usage 的时候，provider 回报的数字才是权威。
- 一条公式不可能匹配每个供应商：口径不同的路由在天花板上差约一成，在地板上差一个瓦片。
- PDF 保持固定价。它的成本跟页数走，而页数不由任何头部声明。
- 老式 `image` 形态的 part 仍按序列化长度计价。这个 harness 没有生产者，而且它会偏高，属于安全
  的一侧。
