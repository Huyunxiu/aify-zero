# 工具结果里的文件跟在一条 user 消息里

中文副本。以 `0039-a-tool-results-file-follows-in-a-user-message.md` 为准。

图片读取的工具结果把字节放成 `file` part，而只有一道闸门决定它是否到达模型：
`hideUnsupportedImages` 问的是**模型**读什么。没有地方问**协议**能装什么，而这两个问题的主语
不同。

chat 协议的工具消息只装文本。除非设了 `supportsMultiPartToolContent`，否则
`@ai-sdk/openai-compatible` 把工具输出写成字符串，而这个 harness 从不设它，于是整个内容数组
（连同 `file` part）在工具消息里变成一段 JSON，文件的字节被写成一张数字表。模型读到的是文本，
不是像素，而且这一回合后面每一步都再发一遍。responses 协议是对的：同一个 part 被它变成图片。

现在一条模型路线同时回答这两个问题。`ModelRoute` 持有协议和输入种类，`route()` 每一步从模型
目标读一次，请求装配在一处应用两条规则：

- 读不了图的模型，字节换成一句话。
- 装不下文件进工具结果的协议，文件移到工具消息紧跟的一条 user 消息里，并在前面写一行说明它们
  回答的是哪次调用。工具结果本来只剩文件时，它留一句话，而不是一个空 part。

顺序就是规则：模型的闸门先跑，读不了的图不会进到 user 消息。

## 考虑过的方案

- **设 `supportsMultiPartToolContent`**：一个开关，没有别的机关。它不在 provider 的公开选项
  里，而且 chat 协议自己的约定是工具消息只装文本；遵守约定的 provider 会拒绝 OpenAI 接受的
  请求。
- **把字节留在工具结果里并说明**：不用改请求的形状。这就是现在的行为，而模型把字节当文本读：
  1 MB 的图每步是几百万字符。
- **在 chat 协议上拒绝读取**：没有要搬的字节。工具不知道协议，因为补丁会在调用与下一次请求之间
  换掉会话的模型；而且这个拒绝会拿走 responses 协议已有的能力。
- **把文件移到 user 消息**（本决定）：工具结果保留它本来就有的一句话，字节以一种所有协议都接受
  的形状到达，重放顺序不变。代价是一条规则，和每个读了文件的 step 多一条消息。

## 后果

- 会话记录仍在工具结果里保留文件，与当初记录的一致。搬动是请求规则，和替换句一样，是复制而不是
  改写。
- responses 协议不受影响，所以两种协议除这一条规则外共用全部规则。
- 只有文件作为内容的工具结果会留一行文字，因为空内容的 part 会被部分 provider 拒绝。
- `ADR 0036` 依然成立：附件是记录，请求是它的一种看法。
