# 日程到点推进，而不是删除

日程是定时器的第二种。它和跟进一样，是会话上一个「下一次触发时刻」；到点后同样往
收件箱写一条待办项，会话因此可能被唤醒。区别只有一处：跟进用完就把行删掉，日程把
行推到下一次。所以一张 `timer` 表、一个扫描循环、一个 id 空间都不变，变的只是事务
末尾那一行收尾。

## 形状

表上只加一列 `recurrence`（JSON，可空），没有 `kind` 列。一类还是两类由
`recurrence IS NULL` 派生；存一列就多一个不一致的可能，而它是纯派生的（ADR 0017
同一条理由）。不变量仍然是「行在 = 还有下一次」：跟进触发后没有下一次，行消失；
日程触发后行推进到下一次。

周期只有三种：`daily`、`weekly`（`weekdays` 表达工作日）、`interval`。`monthly` 与
cron 都不做。周期的全部职责是一个纯函数 `next(rule, { from, after })`，返回严格晚于
`after` 的第一次发生。三条性质由它一个函数给出：

- 首触发是 `next(rule, { from: now })`，没有「先立刻跑一次」的例外。
- 停机期间错过多次只补一次：扫描传的是 `after: now`，不是那个错过的 `dueAt`。
- 相位不漂：`interval` 从旧 `dueAt` 推（`from + k·everySeconds`，k 取最小且结果大于
  `after`），不从 `now` 推。

时区是日历规则的属性，不是日程的属性。写入时把解析后的 IANA 时区固化进规则：来源是
用户设置里的 `timeZone`，没配时取宿主时区。这一行的含义此后不随设置漂移；换时区的
老日程要重设。算术交给 `@js-temporal/polyfill`：这台机器 Node 24.19 的 `Temporal`
默认不可用，而自己用 `Intl` 写「猜测—校正」的出错代价是一年后某个周日少唤醒一次。
夏令时两条约定：当地时刻落在空档里顺延（02:30 → 03:30），落在重复段里取第一次。

工具面加一个 `schedule-set`，`timer-set` 不动；`timer-list` 和 `timer-cancel` 照旧管
两类。撤销就是删除，不做暂停；每会话上限仍是共用的 8。到点正文换成三段：规则、
下一次、迟到（超过两个扫描间隔才提）。`GET /timer/state` 多两个数：生效时区与日程
条数。

## Considered Options

- **另起一张 `schedule` 表**：两张表各自的不变量都不漂移。代价是「写收件箱 + 收尾」
  那段事务要复制，或者抽成参数化的内核——抽完其实就是一个循环管两种来源。而且
  `timer-list` / `timer-cancel` 要跨两张表，模型得先判断一个 id 属于哪一类。
- **用 cron 当底层表示**：表达力更强，加规则不用动表。但 `interval` 是绝对节拍，
  cron 只建模墙钟：`*/2` 是「偶数整点」，不是「每两小时」，而墙钟对齐又表达不出
  「每 90 分钟」。另外每条被接受的规则都得能从 cron 反渲染回人话，否则正文回落到
  原始表达式，模型看到两种正文形状。`recurrence` 本来就是 JSON，加变体不需要迁移，
  cron 唯一的好处在这里不值钱。
- **只做 `daily` / `weekly`，`interval` 推迟**：更小。但用户说「每两小时看一眼」时
  模型没有任何表达方式，只能拒绝或撒谎。推迟并不省下时区算术——日历规则一样要。
- **每条日程由模型显式带时区**：工具入参多一个字段，模型得知道用户在哪；同一个人
  两次设定的日程可能落在两个时区。
- **每次扫描按当前设置现算时区**：用户换时区后老日程自动跟随。代价是扫描循环多一个
  依赖，「行 = 还有下一次」里的时区不再稳定，正文也没法写死下一次。
- **只支持固定偏移时区（不做夏令时）**：省掉 DST 的两条约定。代价是柏林一类的时区
  用不了，而规则里存的是 IANA 名字，降级后语义反而更糟。
- **加暂停状态**：用户说「这周先别提醒」时保留定义。但 `enabled` 是状态列的回归，
  扫描要过滤，`countTimers` 要回答「挂着的算不算停用的」，而且得先定「暂停期间到点
  的那些，恢复后补不补」——没有用户故事。想恢复就重设，`note` 和规则都在上下文里。
- **给界面入口**：日程是用户会直接说的东西。但表单要把三种规则摊给用户，等于把机制
  漏成产品语言；界面现在连定时器列表都没有。可见性可以以后单独做，不挡机制。
- **日程单独一个预算**：两个计数、两个错误码，模型要记两个数。共用 8 时，日程长期
  占位正是想要的约束；嫌少改一个常量即可，不动机制。
- **正文里报「错过几次」**：信息更全。但它的信息量被「迟了多久」覆盖，而对 `interval`
  求次数在长停机时要迭代。
- **把 `recurrence` 塞进 `timer-set`**：工具数不涨，说明集中。但两类入参语言不同，
  合成一个对象就得靠「恰好填一个」的运行时约束，模型写错要多一个来回。

## Consequences

- 收件箱去重键从 `timer:{id}` 改成 `timer:{id}:{dueAt}`：日程的同一个 id 会触发很多
  次，只按 id 去重时，上一次那条还没被领走就会让下一次被 `onConflictDoUpdate` 吞掉。
  旧行不迁移，键不同就不冲突，各自照常被领走。
- 扫描循环形状不变：仍然「写收件箱 → 行收尾」一个事务，提交之后 `wake`。ADR 0012
  的起跑边界没有第二个入口。
- `daily` / `weekly` 的一天是一个当地日历日，跨夏令时相邻两次相隔 23 或 25 小时；
  `interval` 是绝对毫秒，不跟墙钟。两者语义不同，这是不能把 `interval` 编译成 cron
  的同一个理由，也要写进工具描述。
- 换时区设置只影响新日程。老日程按写入时固化下来的时区继续走。
- 停用即删除，恢复靠重设。以后真要保留定义，加 `enabled` 是一次增量迁移，不破现有行。
- 只给模型入口：用户说「每天九点提醒我」时，模型必须真的调 `schedule-set`，它可能
  只在正文里答应。这条靠工具说明和 guidance 缓解，不靠机制兜底——写在这里是为了出事
  时能归因。
- `monthly` 和 cron 变体以后加进来不需要迁移：`recurrence` 是 JSON，判断规则类型的
  代码只有 `next()` 一处。
