# 定时器是收件箱的第三个写入者

用户消息和完成通知之外，收件箱多一个写入者：定时器。一张 `timer` 表存还没到点的
定时器，一个扫描循环每 60 秒把到点的换成收件箱里的一条待办项，然后唤醒会话。到点
不是用户插话，所以投递边界固定是 `run-boundary`；起跑仍然只由运行器负责，扫描循环
只调它的公开 `wake`。

## Considered Options

- **扫描循环直接起跑**：省掉一次入库再出库。但起跑只有运行器一处（ADR 0012），第二条
  路径要长期和它对齐「待办项怎么变成回合」和「跑完了意味着什么」。
- **到点插进正在跑的回合（`step-boundary`）**：看起来更及时。但定时器不是用户说话，
  插进去等于替用户打断；而且正在跑的回合可能在等工具结果，一条提醒会改掉它当步的
  上下文。
- **起跑配置从会话上取**：会话表不存模型，模型只存在每条待办项的 payload 里；运行器
  内存里那份 `#lastPayload` 重启就空。完成通知遇到这种情况可以丢掉，定时器不能丢——
  它是用户唯一在等的那次唤醒。所以 payload 必须跟着定时器行走。
- **扫描间隔 1 秒**：换不来可感知的精度，只换来无谓的查询。60 秒意味着
  `afterSeconds: 600` 实际是十到十一分钟，工具描述里写清楚了。
- **一期同时做日程（周期性）**：日程多出 recurrence、时区来源和停用入口，而仓库里
  没有任何时区处理。跟进只需要一个到期时刻，它验证的是整条链路。

## Consequences

- 到点的两行——写收件箱、删定时器——在同一个事务里：不存在投两次，也不存在丢了
  没投。唤醒在提交之后：在事务里唤醒会让运行器去读还没提交的收件箱，读到空，那条
  待办项就躺到下一次用户说话为止。
- 表里只有未到期的定时器，没有状态列。行在，就是还没触发。
- 暂停的会话照收待办项，运行器不取。暂停是用户按下的刹车，定时器不替他松开。
- 进程重启后启动先扫一次，停机期间到点的全部补投；正文带着「多久之前设的」，让
  模型自己判断这次跟进还成不成立，而不是藏一个过期窗口。
- 子会话没有自己的定时器：它继承父会话的工具，排进来的定时器属于父会话，和后台
  任务同一条规矩。
- 每个会话最多 8 个未到期定时器，上限在写入事务里检查；超了工具层拒绝，模型能看见
  错误并先取消一个。
- 扫描循环有自己的 `GET /timer/state`，不塞进 `GET /runner/state`。它给出四个数：
  扫描间隔、挂着的条数、上次扫描时刻、上次投了几条。后三个分别回答「没到点」
  「扫描停了」「投了但会话没动」；间隔那个数解释精度，60 秒是读者要能看见的。
