# 附件是一条不可变的记录

中文副本。以 `0036-an-attachment-is-an-immutable-record.md` 为准。

`read-file` 早就把图片和 PDF 交给模型了，但做法是把整份文件以 base64 放进工具结果。结果是
每个 step 一列 JSON：字节进了数据库、每次请求都重放、token 估算按编码后的长度计费。读取也
没有任何上限：`readFileBuffer` 来者不拒，一张大照片可以吃掉 agent 进程的内存。

现在读取记录一个引用，而不是字节本身：摘要、媒体类型、大小、所有者和来源路径。字节只写一次，
放在 `<sessionDir>/attachments/<sha256>`，请求装配时再由这个对象生成 file part。

附件不是资源，两者不共用一个名字。资源是 owner 按名字替换的可变文件（ADR 0034）：地址不变
而字节会变，所以字节路由要重定向到版本。附件的地址永远指同一份字节，所以路由直接给出不可变
缓存，不做重定向。会话记录必须重放出当初那次读取产生的字节；一个后续上传可以覆盖的地址做不到
这件事。

## 被否决的选项

- **复用资源通道**（`<sessionDir>/assets/`、`GET /api/asset`）：不需要新路由，界面已经会画资源。
  但它丢掉了记录唯一需要的那条性质——名字可被覆盖；而且图像会继承 2 MB 的上限和不收 GIF 的
  规则，这两条属于头像，不属于读取。
- **继续把 base64 放在 step 里，只加一个上限**：没有存储、没有路由、没有新概念。字节仍然随
  每一次请求和每一行记录走，上限只是改变了被拒的是哪个文件。
- **内容寻址存储**（本决定）：同一份内容只有一个对象，不需要回收器，重放不会漂。代价是第二条
  字节路由，以及一次资源通道本来不需要的写入。
- **本地的 S3 兼容守护进程**：多一个进程，生命周期不归桌面端管——ADR 0034 对资源也是这个理由。

## 后果

- 同一个文件读两次只占一个对象。名字就是摘要，所以并发的写入者不可能在同一地址下发布不同的字节。
- 没有东西回收这些对象。会话是软删除，目录保留，这与 ADR 0034 对资源的说法一致。
- 存的是源字节：这一步没有解码器，所以字节上限表现为拒绝而不是缩放。后续的规范化会用更小的
  派生物替换这次拒绝，而引用不需要改。
- 工具处的拒绝是一句话；历史里当前路由读不了的图，在请求装配时被替换成一句话。同一个谓词回答
  这两处，因为会话会在记录保留旧模型读过的图片时切换模型（ADR 0027）。
