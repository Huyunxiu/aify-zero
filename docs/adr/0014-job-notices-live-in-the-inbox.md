# 完成通知走收件箱的独立种类

后台任务结算后，系统不会主动告诉模型，只有它自己轮询。收件箱是落库的待办项，
运行器只从库里取件起跑，用户消息是唯一的种类。这个决定给收件箱加一个
`job-notice` 种类：完成通知和用户消息共用同一条投递与唤醒路径，不另开通道。

## Considered Options

- **内存通道加新的唤醒入口**：不写库，重启即丢。代价是运行器要多一个唤醒来源，
  待办列表里看不到任务结束。
- **只注入、不唤醒**：改动最小，但空闲会话永远收不到完成通知。
- **收件箱新种类（选中）**：复用运行器、唤醒和待办列表。代价是通知被持久化，
  恢复时要清理指向已不存在任务的项，界面上要和用户消息分开。

## Consequences

- 通知会出现在待办列表，所以一期就要做最小区分：显示成完成提示，不可编辑，
  不进输入框；也不参与「用户插话」判定。
- 任务活不过进程。重启后，指向已不存在任务的通知在恢复时删除，不投递。
- 任务的生命周期记录（注册与结算）留给二期，不塞进通知正文。
- 通知的正文与用户消息同构，协议层不需要为它加第二种消息形状。
