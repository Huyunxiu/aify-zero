# 工具目录靠转调，不把搜到的工具加进声明集

模型用 `search-tools` 搜到 MCP 工具之后，这些工具**不进入**下一步请求的声明集。
模型改用一个恒定的 `call-tool({ name, input })`，由执行层按名字找到真实工具、用它的
schema 校验入参、再执行。`Agent.tools` 不变，每步交给 provider 的工具集合因此恒定。

另一条路是「注入」：搜到就把 schema 加进声明集，下次请求直接给模型
（pi-mono 的 `tool_search` 就是这样，每次最多加 8 个）。

## 为什么选转调

- **不碰 provider 差异**。注入要在会话中途改工具集合，而各家 provider 对「工具集合
  变化」的支持不一样：有的有原生增量投递，有的没有，只能整表重发。本仓库现在没有任何
  这类特化代码，走注入就要新造一层。转调在协议层看起来永远是普通工具调用。
- **工具集合恒定，省下来的是峰值**。注入省的是首屏，峰值仍是「全部声明 + 已加载」；
  而本仓库没有任何缓存标记，每步都整表重发，加载得越多，后续每一步都更贵。
- **服务器会被删**。MCP 服务器存在设置里、运行时可增删。注入只增不减，删掉服务器后
  已加载的工具会变成调不通的悬空项；转调按名字查 `Agent.tools`，查不到就是一个明确
  的错误。

## 代价

- **模型看不到真 schema**。注入有一条后路：搜到之后下一次请求就能看到完整 schema。
  转调没有这条后路，所以搜索结果必须带紧凑参数签名，校验错误必须说清哪个参数不对。
  这是转调方案唯一必须额外做对的地方。（zod 工具已经在执行前校验；MCP 工具的入参
  由服务器自己拒绝，本地没有校验器。）
- **审批要穿透**。审批是按工具名解析服务器与注解的，如果它看到 `call-tool`，就解析不到
  注解，破坏性工具会在没被询问的情况下放行。所以执行层必须先把转调解析成真实工具调用，
  再走 hook 与审批。
- **历史和 UI 分叉**。写回模型的 `tool-result` 必须保留原名 `call-tool`，否则助手消息里
  的调用和结果对不上；而人看的面板需要真实工具名，只能从入参里取。

## Consequences

- 执行层需要一个新的可选入口 `resolveCallTarget`，缺省是恒等。`execution.ts` 因此不需要
  认识 `call-tool` 这个名字，目录扩展也不参与执行。
- `call-tool` 接受任何存在的工具名，包括常驻的内置工具。它因此是一个万能入口——审批
  穿透是它安全的前提，不是可选优化。
- 以后要在目录里加「脚本式访问」（例如 pi-mono 的 `codemode`），入口仍是同一个目录
  数据，不会因为这次选了转调而挡住。
